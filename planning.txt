LLM Planning Today

The current agent already lets the model decide multi-step tool usage: ChemToolsAgent builds a LangGraph ReAct executor with create_react_agent(...) and the full tool registry (CHEMTOOLS_TOOLS) at import time (lang_chain/chemtools_agent.py (lines 24-125), lang_chain/chemtools_wrapper.py (lines 22-159)). Every query is handled by the LLM selecting and sequencing tools on the fly, so routine “small” workflows (normalize → classify → recommend → explain) are already model-planned rather than hard-coded.
You can see a lighter-weight example of this pattern in lang_chain/lang_test.py (lines 146-160), where the system prompt forces a two-step plan (generate → save). That demonstrates how far prompt engineering alone can push the built-in planner.
Beyond ReAct — richer workflows

LangGraph does not yet synthesize novel graphs automatically; you still author the state machine. To give the LLM broader planning authority, add an explicit “planner node” that produces a structured plan and an “executor node” that walks that plan, falling back to tool calls when needed. A minimal sketch:
from langgraph.graph import StateGraph, START, END
from langchain_core.prompts import ChatPromptTemplate
from langchain.output_parsers import JsonOutputParser
from langchain_core.messages import HumanMessage

llm = get_llm_client()  # reuse helper from chemtools_agent

planner_prompt = ChatPromptTemplate.from_messages([
    ("system", "Decompose the chemistry goal into ordered tool calls. "
               "Return JSON with fields steps (list) and rationale."),
    ("human", "{query}")
])
planner_chain = planner_prompt | llm | JsonOutputParser()

def plan_node(state: dict) -> dict:
    plan = planner_chain.invoke({"query": state["query"]})
    return {"plan": plan["steps"], "step_idx": 0, "messages": state["messages"]}

def execute_node(state: dict):
    step = state["plan"][state["step_idx"]]
    ai_reply, updated_history = ChemToolsAgent().chat(
        step, state["messages"], recursion_limit=12, constraints=state.get("constraints")
    )
    return {
        "messages": updated_history,
        "step_idx": state["step_idx"] + 1,
        "last_reply": ai_reply,
    }

graph = StateGraph(dict)
graph.add_node("plan", plan_node)
graph.add_node("execute", execute_node)
graph.add_edge(START, "plan")
graph.add_conditional_edges(
    "execute",
    lambda s: END if s["step_idx"] >= len(s["plan"]) else "execute"
)
workflow = graph.compile()
result = workflow.invoke({"query": user_query, "messages": [HumanMessage(content=user_query)]})
That keeps graph wiring deterministic while letting the LLM propose and adapt a multi-step workflow per request.

If you prefer an off-the-shelf pattern, LangChain’s plan_and_execute helper still works with your toolset: wire the planner to summarize desired steps and reuse ChemToolsAgent.run (or even individual LangChain tools) as the executor. LangGraph can host that by wrapping the two loops in nodes as above.
Practical guidance

Decide whether ReAct + prompt directives are sufficient (least engineering, already running in the CLI) or whether you want persistent, inspectable task plans. The latter justifies building the explicit planner/executor nodes.
Whichever route you take, keep return values structured (dicts/lists) so LangGraph’s state merges cleanly, and cap recursion/loop counts to avoid runaway plans.
Next steps you might consider:

Prototype the planner/executor graph in a notebook to validate that the plan format matches your tool signatures.
Once satisfied, expose it behind a new CLI flag (e.g., --planner) so you can toggle between ReAct and plan-and-execute modes.
